# Portable hosting and CI/CD for the SEFGH Go API, Go pipeline worker and model inference (researched 2026-10-26)

Scope: where to run the Go API, the Go pipeline worker (discover, enrich, analyse, embed) and model inference so that the host or model provider is a settings change, plus the CI/CD to support it. All prices are USD and come from the pages fetched on 2026-10-26 unless a source says otherwise. Prices, quotas and beta features change often; re-check them before committing money. Calculations in "Inferences" are arithmetic on the cited prices, not measurements.

## 1. Google Cloud with $300 credits and the always-free tier (Cloud Run services and jobs, Scheduler, GPUs, Artifact Registry, Secret Manager, Vertex AI)

### Takeaway
Cloud Run services and jobs, Cloud Scheduler (3 free jobs), Artifact Registry (0.5 GB) and Secret Manager (6 secret versions) can host the Go API and a CPU-only worker inside the always-free tier. GPUs need a paid billing account: a Free Trial account must be upgraded first, and the credit still expires 90 days after sign-up. An always-on L4 uses the $300 in about 9 to 12 days. A scale-to-zero L4 batch job costs about $1.05 per hour, so the credit buys roughly 200 to 290 GPU-hours, with each GPU task capped at 1 hour.

### Cited Findings
- Cloud Run services with instance-based billing: free tier (us-central1 pricing) is the first 240,000 vCPU-seconds and 450,000 GiB-seconds per month; on-demand $0.000018 per vCPU-second and $0.000002 per GiB-second — [Cloud Run pricing](https://cloud.google.com/run/pricing)
- Cloud Run services with request-based billing: free tier 180,000 vCPU-seconds, 360,000 GiB-seconds and 2 million requests per month; active CPU $0.000024/vCPU-s, memory $0.0000025/GiB-s, $0.40 per million requests; idle minimum instances $0.0000025/vCPU-s — [Cloud Run pricing](https://cloud.google.com/run/pricing); the same request-based numbers are on [Google Cloud free features](https://docs.cloud.google.com/free/docs/free-cloud-features)
- Cloud Run jobs: free tier 240,000 vCPU-seconds and 450,000 GiB-seconds per month, at the same per-second rates as instance-based services. The page also lists "Delayed Jobs" (342,857 vCPU-s and 642,857 GiB-s free; $0.0000126/vCPU-s, $0.0000014/GiB-s) and worker pools (384,204 vCPU-s and 728,744 GiB-s free; $0.000011244/vCPU-s) — [Cloud Run pricing](https://cloud.google.com/run/pricing)
- The free tier is aggregated across projects by billing account, resets monthly, and is applied as a spending-based discount at Tier 1 prices. Egress has 1 GiB per month free within North America only — [Cloud Run pricing](https://cloud.google.com/run/pricing)
- GPU prices per second (default column): NVIDIA L4 $0.0001867 without zonal redundancy, $0.0002909 with; NVIDIA RTX PRO 6000 $0.00036522 without, $0.00056913 with. A Tier 2 region table lists RTX PRO 6000 at $0.00043826 and $0.00068296. GPU rows appear for services, jobs, delayed jobs and worker pools — [Cloud Run pricing](https://cloud.google.com/run/pricing)
- Google's own example: a 4 vCPU / 16 GiB / L4 (no zonal redundancy) service in europe-west1 that peaks at 2 instances is estimated at $822.40 per month — [Cloud Run pricing](https://cloud.google.com/run/pricing)
- GPU types on Cloud Run: NVIDIA RTX PRO 6000 Blackwell (96 GB VRAM; at least 20 CPU and 80 GiB memory) and NVIDIA L4 (24 GB VRAM; at least 4 CPU and 16 GiB, with 8 CPU and 32 GiB recommended). One GPU per instance; driver 580.x (CUDA 13.0) — [GPU support for services](https://docs.cloud.google.com/run/docs/configuring/services/gpu) (page updated 2026-10-22)
- L4 regions: asia-southeast1, asia-south1 (invitation only), europe-west1, europe-west4, us-central1 and us-east4. RTX PRO 6000 regions: asia-southeast1, asia-south2, europe-west4 and us-central1 — [GPU support for services](https://docs.cloud.google.com/run/docs/configuring/services/gpu)
- GPU services "can scale down to zero for cost savings when not in use." Minimum instances use instance-based billing and are charged at the full rate even when idle. With pre-installed drivers, an instance starts in "approximately 5 seconds." A project's first deployment in a region is automatically granted 3 GPUs of quota (zonal redundancy off); zonal redundancy is on by default for new services — [GPU support for services](https://docs.cloud.google.com/run/docs/configuring/services/gpu)
- Cloud Run jobs with GPUs support the same two GPU types and regions. Jobs support only non-zonal redundancy (set `--no-gpu-zonal-redundancy`). The docs list "batch or offline inference on LLMs" as a use case. GPU billing covers the whole instance lifecycle — [GPU for jobs](https://docs.cloud.google.com/run/docs/configuring/jobs/gpu)
- Job task timeout: "By default, each task runs for a maximum of 10 minutes." It can be raised to 168 hours (7 days), but tasks that use GPUs are limited to 1 hour. With retries on, the timeout applies to each attempt — [Task timeout](https://docs.cloud.google.com/run/docs/configuring/task-timeout)
- Cloud Scheduler costs $0.10 per job per 31 days. "Each Google billing account gets 3 jobs per month free", counted per billing account, not per project. Paused jobs count — [Cloud Scheduler pricing](https://cloud.google.com/scheduler/pricing)
- Always-free amounts: Artifact Registry 0.5 GB of storage per month; Cloud Build 2,500 build-minutes per month on e2-standard-2; Secret Manager 6 active secret versions, 10,000 access operations and 3 rotation notifications per month — [Google Cloud free features](https://docs.cloud.google.com/free/docs/free-cloud-features)
- The $300 Welcome credit is valid for 90 days. While the billing account is a Free Trial account, you cannot add GPUs to VMs or request quota increases. After upgrading to a paid account, restricted products "such as GPUs, Google Cloud Marketplace, and third-party generative AI models" become available, and the remaining credit can be used only within the original 90 days — [Google Cloud free features](https://docs.cloud.google.com/free/docs/free-cloud-features)
- Vertex AI appears to have been renamed. The free-tier list now shows "Agent Runtime on Gemini Enterprise Agent Platform" (first 180,000 vCPU-seconds and 360,000 GiB-seconds per month) — [Google Cloud free features](https://docs.cloud.google.com/free/docs/free-cloud-features). The OpenAI-compatibility page is titled "Gemini Enterprise Agent Platform", and its examples use `google/gemini-3.5-flash` — [OpenAI compatibility](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/start/openai)
- Cloud Run rollouts: `gcloud run deploy --image IMAGE --no-traffic --tag TAG_NAME` creates a revision with no traffic and its own tagged URL (`https://TAG---service-xxxx.a.run.app`). `gcloud run services update-traffic SERVICE --to-revisions REVISION=PERCENTAGE` shifts traffic in steps; `REVISION=100` rolls back; `--to-latest` sends all traffic to the newest revision — [Rollouts, rollbacks and traffic migration](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration)

### Inferences
- **Always-on L4** (no zonal redundancy): the GPU alone costs $0.0001867 x 86,400 = about $16.13 per day. The minimum 4 vCPU + 16 GiB adds (4 x 0.000018 + 16 x 0.000002) x 86,400 = about $8.99 per day, for about $25.1 per day in total. $300 lasts about 12 days, or about 8.8 days at the recommended 8 vCPU / 32 GiB (about $34.1 per day). With zonal redundancy (the default for services) at 4 vCPU, it is also about $34.1 per day. An always-on RTX PRO 6000 (20 vCPU / 80 GiB) is about $76.5 per day, which lasts about 4 days.
- **Batch L4 job** (4 vCPU / 16 GiB, scale to zero): about $0.000291 per second, which is about $1.05 per hour, or about 287 GPU-hours for $300. At 8 vCPU / 32 GiB it is about $1.42 per hour, or about 211 GPU-hours. The 1-hour task cap means the worker has to split work into resumable shards that each finish in under 1 hour (for example N repositories per task, with progress in Postgres).
- How many summaries fit in a GPU-hour is unknown without a benchmark of the chosen model. AGENTS.md forbids performance claims without measurements, so the first GPU spend should be a small measured run.
- **CPU-only worker in the free tier:** 240,000 vCPU-seconds is about 66.7 vCPU-hours per month. A 1 vCPU / 0.5 GiB Cloud Run job can therefore run about 66 hours a month for free, which covers I/O-bound discover, enrich and embed steps that call remote model APIs.
- **Scheduling:** 3 free Scheduler jobs are enough for discover, enrich and a nightly analyse/embed. pg_cron in Supabase can also call an HTTP tick, which keeps the schedule with the data and stays the same across hosts.
- **Secrets:** 6 free Secret Manager versions is tight if the worker needs several GitHub tokens plus summariser, embedder and reranker keys and a database URL. Rotating a secret creates a new version, so keep old versions disabled or destroyed, or group values per role.
- **Credit timing:** the 90-day expiry, not the $300, is the likely binding limit for light use. Do GPU experiments within the 90 days, and keep the steady-state API and worker inside the always-free amounts so nothing changes when the credit ends.
- The Agent Platform (Vertex) OpenAI-compatible endpoint authenticates with a 1-hour OAuth access token, not a static key. A provider registry therefore needs an auth type such as `gcp-adc` in addition to `bearer`.

### Gaps
- None of the fetched pages states whether Cloud Run GPUs (services or jobs) are GA or preview.
- Gemini / Agent Platform model prices per token and embedding-model availability through the OpenAI-compatible endpoint were not researched. The page only shows chat completions.
- Cloud Run GPU cold-start time including model weight loading (as opposed to the 5-second driver start) is not documented. It depends on model size and must be measured.

## 2. Vercel: Go runtime status, Hobby function and Cron limits, Services, Daemons, Queues, Workflow, Sandbox, and whether a long-running worker belongs there

### Takeaway
As of 2026-10-26, the Vercel Go runtime, Services and the Container runtime are Beta, and Daemons (long-running container workers) are Public Beta, all available on Hobby. Hobby limits are small, though: 300 s per function, 4 Active CPU hours a month for functions, 5 Active CPU-hours a month for daemons, cron at most once a day, and non-commercial use only. Daemons do not run in preview deployments. Vercel suits the Go API and short ticks. The heavy pipeline and GPU inference belong elsewhere, with Vercel Daemons kept as one possible target for the same worker image.

### Cited Findings
- "The Go runtime is available in Beta on all plans." The Go Framework Preset detects a root `go.mod` and one of `main.go`, `cmd/api/main.go` or `cmd/server/main.go`, and the server must listen on `PORT`. The Go version comes from `go.mod` (a `toolchain` directive wins). Default build flags are `-ldflags '-s -w'`; you can override them with `GO_BUILD_FLAGS` or a `buildCommand` such as `go build -o server ./cmd/api`. `go.mod` must be at the project root — [Vercel Go runtime](https://vercel.com/docs/functions/runtimes/go) (updated 2026-08-11)
- Fluid compute function limits: Hobby has a 300 s maximum duration (default and maximum) and 2 GB / 1 vCPU. Pro has a 300 s default, an 800 s maximum and up to 1,800 s in beta, and up to 4 GB / 2 vCPU — [Vercel limits](https://vercel.com/docs/limits) (updated 2026-09-16)
- Other Hobby limits: 100 deployments created per day; 1 concurrent build; 45-minute build limit; runtime logs kept 1 hour; proxied request timeout (rewrites to an external destination) of 120 s on all plans. A Hobby project cannot be connected to a Git repository owned by a Git organization — [Vercel limits](https://vercel.com/docs/limits)
- Hobby monthly allotments: 100 GB Fast Data Transfer, 1,000,000 function invocations, 10 GB Fast Origin Transfer, 4 hours Active CPU, 360 GB-hours provisioned memory. Pro on-demand rates: Active CPU from $0.128 per hour, provisioned memory from $0.0106 per GB-hour, $0.60 per million invocations — [Fair use guidelines](https://vercel.com/docs/limits/fair-use-guidelines) (updated 2026-09-14)
- "Hobby teams are restricted to non-commercial personal use only." Asking for donations is not commercial use — [Fair use guidelines](https://vercel.com/docs/limits/fair-use-guidelines)
- Cron: 100 cron jobs per project on every plan. On Hobby, the minimum interval is once per day and precision is per hour (±59 min); more frequent expressions fail at deployment. Pro allows once per minute with per-minute precision — [Cron usage and pricing](https://vercel.com/docs/cron-jobs/usage-and-pricing) (updated 2026-07-15)
- Services: "Services are available in Beta on all plans." The `services` key in `vercel.json` defines each service. A service is private until a top-level rewrite such as `{ "source": "/api/(.*)", "destination": { "service": "api" } }` exposes it. Private service bindings inject the target's URL as an environment variable. A service can be built from a Dockerfile with `"runtime": "container"`. Background workers that pull their own work should use Daemons instead — [Vercel Services](https://vercel.com/docs/services) (updated 2026-08-10)
- Container runtime: "Container Runtime is available in Beta on all plans." Vercel builds a root `Dockerfile` or `Containerfile` (or `Dockerfile.vercel`), pushes it to Vercel Container Registry (VCR) and runs it as a Function with Active CPU pricing. The default port is 80 and can be overridden with `PORT`. Instances scale down after 5 minutes without traffic in production (30 s in preview) and receive SIGTERM with a 30 s grace period. Normal Function limits apply — [Container runtime](https://vercel.com/docs/functions/runtimes/container) (updated 2026-07-07)
- VCR: storage costs $0.10 per GB. Images can be up to 15 GB total with 2 GB per compressed layer. Hobby allows 10 repositories per project and 50 images per repository. Layers must be gzip or zstd — [VCR limits and pricing](https://vercel.com/docs/container-registry/limits-and-pricing) (updated 2026-09-22)
- Daemons: "Daemons are available in Public Beta on all plans." They run long-running processes from container images, such as queue consumers and job runners. During the beta, daemons run only in production deployments; there is no inbound HTTP, no autoscaling and only ephemeral storage. Instances are linux/amd64 with 1, 2, 4 or 8 GiB of memory. On shutdown they get SIGTERM with a 30 s grace period (configurable up to 3,600 s). Each instance receives a Vercel OIDC token file — [Vercel Daemons](https://vercel.com/docs/daemons) (the page metadata shows "last_updated: 2018-10-20", which is clearly wrong)
- Daemon quotas: Hobby allows 1 or 2 GiB (1 vCPU) instances and 5 Active CPU-hours per month per team; time spent waiting does not count. When a Hobby team reaches the quota, Vercel stops its daemons until the 1st of the next month (UTC). Pro allows 16 vCPUs and 32 GiB running at once and bills Active CPU plus provisioned memory. Projects whose root directory is a subfolder (such as `apps/web`) cannot add daemons yet — [Daemons limits](https://vercel.com/docs/daemons/limits)
- Queues: billed per API operation, metered in 4 KiB chunks; Hobby includes the first 1,000,000 operations. Retention is 60 s to 7 days (default 24 h), the visibility timeout is up to 60 minutes, and the maximum message size is 100 MB — [Queues pricing](https://vercel.com/docs/queues/pricing) (updated 2026-08-12)
- Workflows: Hobby includes 50,000 events and 1 GB of data written per month. On-demand prices are $0.02 per 1,000 events, $0.50 per GB written and $0.50 per GB-month retained (retention is not available on Hobby). A run is limited to 25,000 events and 10,000 steps on the Node.js runtime, and each step's runtime is bounded by Function limits. Workflows run on Node.js or the experimental QuickJS runtime — [Workflow pricing](https://vercel.com/docs/workflows/pricing) (updated 2026-09-16)
- Sandbox on Hobby includes 5 Active CPU hours, 420 GB-hours of memory, 5,000 creations and 20 GB of data transfer per month. Hobby sessions last at most 45 minutes with 4 vCPU / 8 GB and 10 concurrent sandboxes. Pro allows 24-hour sessions at $0.128 per CPU-hour — [Sandbox pricing](https://vercel.com/docs/vercel-sandbox/pricing) (updated 2026-09-10)
- Instant Rollback: "Hobby users can roll back to the immediately previous deployment." Pro can roll back to any deployment that was previously in production. A rollback does not change environment variables and turns off auto-assignment of production domains until it is undone with `vercel promote` — [Instant Rollback](https://vercel.com/docs/instant-rollback) (updated 2026-07-07)

### Inferences
- The same OCI image of a Go command can run on Vercel (Container runtime for HTTP, a Daemon for the worker), on Cloud Run and on a home server. That makes Vercel one deploy target rather than a special case. Daemons do not run in preview deployments and need a Dockerfile, so CI must test the worker image directly instead of relying on Vercel previews.
- If the SEFGH Go API Vercel project uses a Root Directory such as `backend/`, daemons cannot be added to that project during the beta. Check this before planning a Vercel daemon.
- The Go preset detects only one entrypoint. For a repo with both `cmd/api` and `cmd/worker`, pin `buildCommand` to `go build -o server ./cmd/api` so the API project never builds the worker by accident.
- A tick on Hobby is limited to 300 s per call and shares the 4 Active CPU hours per month. LLM and embedding calls are mostly waiting on I/O, which does not count as Active CPU, so a tick that only orchestrates remote model calls fits better than one that parses or embeds locally. Vercel Cron on Hobby can run only once a day, so pg_cron (or Cloud Scheduler) is the more frequent and more portable trigger.
- If the Next.js site rewrites a route to a Go API on another host (Cloud Run or home server), the 120 s proxied-request timeout applies to that route.
- Vercel Workflows are JavaScript/TypeScript only, so they do not fit a Go worker without a JS wrapper. Vercel Queues have an HTTP API but were not checked for Go consumers.
- SEFGH may become commercial (ads, paid tiers). Hobby forbids that, so plan for Vercel Pro or moving off Vercel at that point.

### Gaps
- The Vercel Go runtime page does not say whether Go 1.27 is supported yet. It downloads the toolchain named in `go.mod`, but this was not tested.
- Whether Vercel Queues can be consumed from Go (HTTP API or poll mode) was not checked.
- Vercel has no GPUs. Vercel AI Gateway (hosted model routing) was not researched here.

## 3. Other free or cheap hosts for a Go container in 2026: Fly.io, Render, Koyeb, Railway, Northflank, Cloudflare Containers

### Takeaway
No host gives a truly free, always-on container with worker support in 2026. Render's free web services sleep after 15 minutes and workers are not free. Koyeb's single free instance sleeps after 1 hour, cannot be a worker, and Koyeb is joining Mistral AI. Fly.io has no free tier for new organizations and stopped offering GPUs after 1 August 2026. Railway gives $1 of credit a month. Northflank's free Sandbox (2 services, 2 jobs, cron, BYOC on GCP) is the most capable free option. Cloudflare Containers needs the $5 Workers Paid plan. For cheap GPUs outside Google, Koyeb (L4 $0.70/h) and Northflank (L4 $0.80/h) are the listed options.

### Cited Findings
- Fly.io: "New organizations don't have a free tier or a monthly free usage allowance." New accounts get a trial of up to 2 hours of Machine runtime or 7 days, whichever comes first. shared-cpu-1x costs $2.19 per month at 256 MB, $3.69 at 512 MB and $6.70 at 1 GB (continuous, iad/ewr). Stopped Machines pay $0.15/GB/month for their root filesystem. Organizations on plans discontinued in October 2024 keep their free allowances — [Fly.io pricing](https://docs.fly.io/about/pricing)
- Fly.io GPUs are deprecated. A Fly community announcement says they end July 31, 2026, and Fly's docs reportedly say they are unavailable after August 1, 2026 — [Fly community: GPU migration](https://community.fly.io/t/gpu-migration-fly-io-gpus-will-be-deprecated-as-of-july-31-2026/27110); [fly.io/gpus](https://fly.io/gpus) (the docs wording comes from the search summary, not a direct fetch)
- Render: a free web service spins down after 15 minutes without inbound traffic and takes about one minute to wake. Each workspace gets 750 free instance hours per month. Free Render Postgres databases expire 30 days after creation, with a 14-day grace period. "Other service types don't support Free instances", so background workers and cron jobs are paid — [Render free tier](https://render.com/docs/free)
- Koyeb: one Free Instance per organization, 512 MB RAM, 0.1 vCPU and 2 GB SSD, in Frankfurt or Washington, D.C. only. It "scale[s] down to zero when [it doesn't] receive any traffic for 1 hour" and cannot be a Worker Service or use volumes. The smallest paid instance is eco-nano at $1.61 per month. The page carries the banner "Koyeb is joining Mistral AI" — [Koyeb instances](https://www.koyeb.com/docs/reference/instances) (last updated May 27, 2026)
- Koyeb plans: Pro $29/month plus compute (includes $10 of compute) and Scale $299/month. GPU prices: L4 $0.70/h, L40S $1.20/h, A100 80 GB $1.60/h, H100 $2.50/h — [Koyeb pricing](https://www.koyeb.com/pricing)
- Third-party reports say Mistral AI acquired Koyeb in February 2026 and that new users may no longer get the free Starter plan. These reports conflict and are unverified — [Kuberns: Koyeb alternatives](https://kuberns.com/blogs/koyeb-alternatives/); [SnapDeploy](https://snapdeploy.dev/blog/koyeb-vs-free-container-tier)
- Railway: the Free plan is $0 "with $1 of free credit per month" and allows 1 replica, 0.5 GB RAM, 1 vCPU and a 0.5 GB volume. A new Trial gets a one-time $5. Hobby costs $5/month including $5 of usage. Container prices are $10/GB RAM/month, $20/vCPU/month and $0.05/GB egress; builds are free — [Railway plans](https://docs.railway.com/reference/pricing/plans)
- Northflank: the free Sandbox plan allows 2 services, 2 jobs and 1 database add-on, "up to $20/mo of resources" on Northflank Cloud, and 1 BYOC cluster (up to 12 vCPU / 48 GB), with "no card needed". Pay-as-you-go starts at $0.01667 per vCPU-hour and $0.00833 per GB-hour; BYOC is $0.02083 per node vCPU-hour, with Google Cloud listed among BYOC providers. Jobs can run "on a cron schedule or as a one off". GPU prices: L4 $0.80/h, A100 40 GB $1.42/h, RTX PRO 6000 $3.00/h — [Northflank pricing](https://northflank.com/pricing)
- Cloudflare Containers require the Workers Paid plan ($5/month), which includes 25 GiB-hours of memory, 375 vCPU-minutes and 200 GB-hours of disk per month. Overage is $0.000020 per vCPU-second and $0.0000025 per GiB-second. Instance types range from lite (1/16 vCPU, 256 MiB) to standard-4 (4 vCPU, 12 GiB). "Charges stop after the container instance goes to sleep." Requests go through a Worker and a Durable Object, which are billed too. The page mentions no GPU — [Cloudflare Containers pricing](https://developers.cloudflare.com/containers/pricing/)

### Inferences
- Of these, only Northflank's free Sandbox offers a scheduled job (cron) plus a service at no cost. Its BYOC option could run inside the owner's Google Cloud project and spend the GCP credits, but that adds a Kubernetes cluster to manage and was not priced here.
- Koyeb's future as a general host is uncertain after the Mistral deal. Treat it as a possible GPU-inference provider, not a home for the API.
- Fly.io is a poor fit now: no free tier, and no GPUs from August 2026.
- Because none of these is free and always-on with worker support, the portable design matters more than the choice of host. Build the same image, configure it only through environment variables, and keep a deploy script per target.

### Gaps
- Northflank's free Sandbox wording ("up to $20/mo of resources") does not make clear whether that is a free allowance or a cap. Check it at sign-up.
- Render's free bandwidth and build-minute numbers are not on its free-tier page.
- Cloudflare Containers' GA or beta status and any GPU plans were not on the pricing page.

## 4. Self-hosting later on a small server: Docker Compose, Coolify, Dokploy, Kamal 2, Caddy, Ollama / llama.cpp / vLLM in containers, Supabase self-hosted vs plain Postgres + pgvector, backups

### Takeaway
A small server can run the same images with plain Docker Compose behind Caddy, or with a deploy tool. Kamal 2 (via kamal-proxy) gives healthchecked, gapless deploys and Let's Encrypt with a few lines of YAML. Coolify gives a web UI and needs about 2 cores, 2 GB and 10 GB. Local inference servers (Ollama, llama.cpp `llama-server`, vLLM) all speak the OpenAI-compatible API, so switching between a cloud provider and the home server is a base-URL change. Self-hosted Supabase needs at least 4 GB of RAM and makes you responsible for TLS, SMTP, secrets and upgrades. Moving to plain Postgres + pgvector is simpler but would mean replacing Supabase Auth, Storage and Realtime.

### Cited Findings
- Kamal (docs show version 2.12.0) uses kamal-proxy for "gapless deployments" on ports 80/443. With `ssl: true`, a single server and a `host` pointing to it, kamal-proxy obtains Let's Encrypt certificates. It healthchecks `/up` by default (every second, 5 s timeout), configurable through `healthcheck: { path, interval, timeout }`. Several apps share one proxy, routed by `host` — [Kamal proxy configuration](https://kamal-deploy.org/docs/configuration/proxy/)
- Coolify self-hosted needs at least 2 CPU cores, 2 GB RAM and 10 GB free disk, on amd64 or arm64 Linux only. It "can run on smaller servers (for example: 1 CPU core, 512 MB RAM, 4 GB disk), but this is not recommended" — [Coolify installation](https://coolify.io/docs/get-started/installation)
- Coolify vs Dokploy, from secondary sources: Coolify drives Docker/Compose over SSH, while Dokploy runs on Docker Swarm; both use Traefik with automatic SSL. One article puts Dokploy at about 350 MB RAM idle and Coolify at 500 MB to 1.2 GB. Coolify is Apache-2.0; Dokploy is Apache-2.0 except a `/proprietary` folder under a source-available licence that needs a commercial agreement for production use — [getdeploying: Coolify vs Dokploy](https://getdeploying.com/guides/coolify-vs-dokploy); [LumaDock comparison](https://lumadock.com/tutorials/coolify-vs-dokploy) (vendor-adjacent sources; verify the Dokploy licence directly)
- Supabase self-hosting with Docker needs at least 4 GB RAM, 2 cores and 40 GB SSD; 8 GB+, 4 cores+ and 80 GB+ SSD are recommended. The stack runs Studio, Envoy (API gateway; Kong is an optional override), Auth, PostgREST, Realtime, Storage, imgproxy, postgres-meta, Postgres, Edge Runtime and Supavisor, plus optional Logflare and Vector. You handle HTTPS (Supabase suggests a reverse proxy such as Caddy or Nginx), SMTP and secrets. Secrets live in `.env` by default, and a secrets manager is "strongly recommend[ed]" for production. Stable Compose snapshots ship about monthly, and `update.sh` merges them — [Supabase self-hosting with Docker](https://supabase.com/docs/guides/self-hosting/docker)
- Supabase hosted Free plan: 500 MB database, 5 GB egress, paused after 1 week of inactivity, 2 active projects, no automatic backups, and 1-day log retention. Pro includes daily backups kept 7 days — [Supabase pricing](https://supabase.com/pricing.md)
- Ollama's OpenAI-compatible API is at `http://localhost:11434/v1/`, with `/v1/chat/completions`, `/v1/completions`, `/v1/models`, `/v1/embeddings` and `/v1/responses`. Locally the API key is "required but ignored". Limits include no `tool_choice`, logprobs or `n` in chat, and no token-array input for embeddings — [Ollama OpenAI compatibility](https://docs.ollama.com/api/openai-compatibility)
- llama.cpp `llama-server` offers OpenAI-compatible chat, responses and embeddings routes (`/v1/embeddings`) and reranking (`/v1/rerank` with `--rerank`). It supports `--api-key` or `--api-key-file`, and `GET /health` returns 503 while loading and 200 `{"status": "ok"}` when ready. Docker images are `ghcr.io/ggml-org/llama.cpp:server` (CPU) and `:server-cuda` — [llama.cpp server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)
- vLLM's official image is `vllm/vllm-openai`. Its example runs with `--runtime nvidia --gpus all -p 8000:8000 --ipc=host --model Qwen/Qwen3-0.6B` and serves an OpenAI-compatible server. Listed platforms are NVIDIA CUDA, AMD ROCm, Intel XPU and Apple Silicon — [vLLM Docker deployment](https://docs.vllm.ai/en/latest/deployment/docker.html)

### Inferences
- **Simplest path for a single small server:** Docker Compose with Caddy (automatic TLS) in front of `sefgh-api`, a `sefgh-worker` that runs on a schedule or loops, and `llama-server` or Ollama for inference. Kamal 2 adds healthchecked gapless deploys from GitHub Actions over SSH with no control-plane service on the box. Coolify or Dokploy add a UI at a cost of about 0.35 to 1.2 GB of RAM.
- **Inference choice:** llama.cpp `llama-server` covers chat, embeddings and reranking from one binary with an API key and a health endpoint, which matches the summariser / embedder / reranker roles. vLLM needs a real GPU. Ollama is the easiest on CPU or a small GPU but lacks reranking in its OpenAI layer.
- **Database:** keep hosted Supabase while the website depends on Supabase Auth, Storage and Realtime (an AGENTS.md constraint). Self-hosted Supabase (at least 4 GB RAM) on the same small box as inference would compete for memory. Plain Postgres + pgvector suits only a worker-side database and would mean re-implementing auth.
- **Backups:** the Supabase Free plan has no automatic backups, so a scheduled logical dump (for example a GitHub Actions or Cloud Run job running `pg_dump` to private storage) is needed whichever host is chosen. Self-hosted Supabase backups are not covered on the fetched page.
- **Embeddings:** a local embedding model must be the same model and dimension as the stored vectors (AGENTS.md). Moving the embedder to the home server is a migration with a re-embed, not a configuration flip.

### Gaps
- Caddy's own docs, the Dokploy docs and the Kamal 2 install requirements were not fetched directly.
- Whether vLLM's server supports an API key option was not on the fetched page.
- Self-hosted Supabase backup tooling and branching parity were not covered on the fetched page.

## 5. Packaging: one image per Go command (distroless/static, ko, multi-stage Docker), image signing and SBOM, reproducible builds

### Takeaway
Build each command (`cmd/api`, `cmd/worker`) with `CGO_ENABLED=0 go build -trimpath` into a distroless `static-debian13:nonroot` image of about 2 MiB plus the binary. Use a multi-stage Dockerfile as the canonical recipe, because Vercel (Container runtime and Daemons), Cloud Build, Compose and Kamal all build from Dockerfiles; ko is an optional faster Docker-free builder that emits SBOMs. GitHub artifact attestations do not work in private repositories without GitHub Enterprise Cloud, so signing for a private repo means cosign keyless, which has a privacy trade-off.

### Cited Findings
- ko "builds images by executing `go build` on your local machine, and as such doesn't require `docker`". It produces SBOMs by default, makes multi-platform builds easy, and suits single-binary apps with "no cgo, no OS package dependencies" — [ko](https://ko.build/)
- Distroless: `gcr.io/distroless/static-debian13` (tags latest, nonroot, debug, debug-nonroot; amd64, arm64 and others) is "around 2 MiB". "All distroless images are signed by cosign with ephemeral keys (keyless)", and the project recommends verifying with `cosign verify ... --certificate-oidc-issuer https://accounts.google.com --certificate-identity keyless@distroless.iam.gserviceaccount.com` — [distroless](https://github.com/GoogleContainerTools/distroless)
- Reproducible builds: "As of Go 1.21, the Go toolchain is perfectly reproducible". For programs without cgo, "a reproducible build is as simple as compiling with `CGO_ENABLED=0 go build -trimpath`" — [Go blog: Perfectly Reproducible, Verified Go Toolchains](https://go.dev/blog/rebuild) (28 August 2023)
- GitHub artifact attestations: `actions/attest@v4` with `id-token: write`, `attestations: write` and `packages: write` attests image provenance (`subject-digest`, `push-to-registry: true`) and SBOMs (`sbom-path`). Verify with `gh attestation verify oci://ghcr.io/ORG/IMAGE -R ORG/REPO` — [Use artifact attestations](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations)
- Artifact attestations work in public repositories on all current plans, but private and internal repositories need GitHub Enterprise Cloud — [Using artifact attestations](https://docs.github.com/actions/security-guides/using-artifact-attestations-to-establish-provenance-for-builds) (from the search summary of the official docs)
- Vercel Daemons need a `Dockerfile` or `Containerfile` in the daemon's root ("Builds without a Dockerfile" is unsupported), and the Container runtime builds from a Dockerfile — [Daemons limits](https://vercel.com/docs/daemons/limits); [Container runtime](https://vercel.com/docs/functions/runtimes/container)

### Inferences
- **Suggested layout:** one `backend/Dockerfile` with `ARG CMD=api`. The build stage runs `CGO_ENABLED=0 go build -trimpath -ldflags='-s -w' -o /out/app ./cmd/${CMD}`, and the final stage is `FROM gcr.io/distroless/static-debian13:nonroot` with `COPY --from=build /out/app /app`, `USER nonroot` and `ENTRYPOINT ["/app"]`. Build `sefgh-api` and `sefgh-worker` from the same file. The project already uses only the standard library and no cgo, which matches ko's and distroless's best case.
- Pin the base image by digest and verify its cosign signature in CI, so the image can be rebuilt reproducibly.
- **Private repo on GitHub Free or Pro:** GitHub attestations are not available. Use `cosign sign --yes` keyless with the GitHub OIDC token, plus an SBOM from ko or `docker buildx --sbom`. Keyless signing records the signing identity (repository and workflow path) in the public Sigstore transparency log, which exposes the private repo's name. If that matters, use a cosign key pair kept in a secret or Google Cloud KMS, or skip signing until the repo is public.
- Push to one registry (GHCR or Artifact Registry) and deploy by digest everywhere. Artifact Registry's 0.5 GB free tier holds only a few tags of a small distroless image, so add cleanup policies.

### Gaps
- ko's default base image, its SBOM format and `ko-build/setup-ko` were not on the fetched landing page.
- Whether the distroless static image includes CA certificates and tzdata (needed for HTTPS calls to GitHub and model APIs) was not stated on the fetched page.
- GHCR storage limits and costs for private packages were not checked.

## 6. CI/CD in GitHub Actions: Workload Identity Federation, environments and reviewers, previews, path filters, Go caching, deploy-on-tag, rollbacks; Supabase CLI in CI; Vercel CLI and Git integration

### Takeaway
Use Workload Identity Federation (`google-github-actions/auth@v3`, `id-token: write`) so no Google key is stored. On GitHub Free, a private repo gets no environment secrets, required reviewers or wait timers, so approvals have to be modelled differently, or the account upgraded. Path-filtered workflows must not be required checks, because skipped workflows leave required checks pending. `actions/setup-go@v7` caches by default. Vercel deploys from Actions still need a static `VERCEL_TOKEN` (no OIDC). Supabase Branching is not available on Free, so migrations are checked with `supabase db lint`, `db diff`, `db push --dry-run` and the existing native Postgres test.

### Cited Findings
- `google-github-actions/auth@v3`: "(Preferred) Direct Workload Identity Federation", which is recommended over service account keys. The workflow needs `id-token: 'write'`. Inputs are `workload_identity_provider` (`projects/NUM/locations/global/workloadIdentityPools/POOL/providers/PROVIDER`) and `project_id`, plus `service_account` only for the impersonation flow, which is needed for OAuth or ID tokens. "Always add an Attribute Condition", for example `assertion.repository_owner == '${GITHUB_ORG}'`. Setup uses `gcloud iam workload-identity-pools create` and `providers create-oidc --issuer-uri="https://token.actions.githubusercontent.com"`. Propagation takes up to 5 minutes — [google-github-actions/auth](https://github.com/google-github-actions/auth)
- Environments on private repositories: "If you are on a GitHub Free, GitHub Pro, or GitHub Team plan, required reviewers are only available for public repositories." Wait timers are the same. Deployment branch rules work on private repos only on Pro and Team. "If you are using GitHub Free, environment secrets are only available in public repositories." An environment can list up to 6 reviewers, only one has to approve, and "prevent self-review" is available — [Deployments and environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments)
- A required check whose workflow is skipped by path or branch filtering or a commit message stays "Pending" and blocks merging. GitHub's advice: "Avoid requiring workflows that can be skipped." — [Troubleshooting required status checks](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/troubleshooting-required-status-checks)
- `actions/setup-go@v7`: "caching is enabled by default" (turn it off with `cache: false`). `go-version-file` reads `go.mod` (the `toolchain` directive wins). The default module cache key is based on `go.mod`; set `cache-dependency-path` to use `go.sum` or multiple files — [actions/setup-go](https://github.com/actions/setup-go)
- GitHub Actions pricing: hosted runner prices dropped by up to 39% from January 1, 2026. The planned $0.002 per minute charge for self-hosted runners (from March 1, 2026) was postponed in December 2025 — [GitHub changelog 2025-12-16](https://github.blog/changelog/2025-12-16-coming-soon-simpler-pricing-and-a-better-experience-for-github-actions/); [GitHub resources: 2026 pricing changes](https://resources.github.com/actions/2026-pricing-changes-for-github-actions/)
- Vercel from GitHub Actions: store `VERCEL_TOKEN`, `VERCEL_ORG_ID` and `VERCEL_PROJECT_ID` as secrets, then run `vercel pull --yes --environment=preview|production`, `vercel build [--prod]` and `vercel deploy --prebuilt [--prod]`. Set `"git": { "deploymentEnabled": false }` to stop double deploys. "Vercel doesn't currently support OIDC for authenticating the GitHub Actions deployment itself" — [Vercel KB: GitHub Actions](https://vercel.com/kb/guide/how-can-i-use-github-actions-with-vercel)
- Vercel Instant Rollback on Hobby goes only to the immediately previous deployment, and afterwards production domain auto-assignment stays off until `vercel promote` — [Instant Rollback](https://vercel.com/docs/instant-rollback)
- Cloud Run gives a canary and rollback path: deploy with `--no-traffic --tag`, test the tagged URL, then `update-traffic --to-revisions REV=N`, and roll back with `REV=100` on the previous revision — [Cloud Run rollouts and rollbacks](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration)
- Supabase CLI: `supabase db lint` runs `plpgsql_check` and fails CI with `--fail-on warning|error` (the default `none` always exits 0). It targets `--local`, `--linked` or `--db-url`. `supabase db diff` compares migrations against a shadow database; the legacy migra engine can miss publications, storage buckets and `security_invoker` views. `supabase db push --dry-run` lists pending migrations without applying them. `supabase migration list` compares local and remote history. `supabase test db` runs pgTAP tests in `supabase/tests` — [supabase db lint reference](https://supabase.com/docs/reference/cli/supabase-db-lint)
- Supabase Branching is "Not included" on Free and costs $0.01344 per branch per hour on Pro and Team. It is "available on the Pro Plan and above" — [Supabase pricing](https://supabase.com/pricing.md). With the GitHub integration, a preview branch per pull request builds from the repository migrations and is deleted when the PR closes — [Supabase branching](https://supabase.com/docs/guides/deployment/branching)

### Inferences
- **Approvals on GitHub Free without environment features:** gate production deploys on `push: tags: ['v*']` (or `workflow_dispatch`) with branch protection on `main`, and keep WIF trust narrow. The WIF attribute condition can require `assertion.ref == 'refs/heads/main'` or a tag ref, so only main or tag runs can deploy. That condition is enforced by Google, not GitHub, so it works on GitHub Free. Upgrading to GitHub Pro restores branch rules but still not required reviewers on private repos (that needs Enterprise or a public repo).
- **Saving minutes with path filters while keeping required checks:** run one always-on "gate" job that uses a changes detector (for example `dorny/paths-filter`, not researched here) and conditionally skips the expensive Go, contract and browser jobs inside the same workflow. Only the gate job is a required check, so nothing is left pending.
- **Deploy flow for portability:** on a PR, build images, run `go test -race`, `go vet` and contracts, and build `--no-traffic` tagged Cloud Run revisions or Vercel previews for the API. On a tag, push images by digest, deploy to the active target, run the production forwarding probe against the tagged URL, then shift traffic. Rollback means re-pointing traffic or the Vercel rewrite, not rebuilding.
- **Database in CI:** keep the existing native Postgres test as the migration gate, and add `supabase db lint --fail-on error` plus `supabase db push --dry-run --linked` (read-only; needs a link secret) as advisory steps. Owner approval for applying migrations stays manual, which fits the lack of Branching on Free.
- **Vercel token:** a long-lived `VERCEL_TOKEN` cannot be scoped to an environment secret in a private repo on GitHub Free, so it becomes a repository secret that every workflow can read. Restrict which workflows reference it and keep `pull_request_target` out of deploy workflows. Alternatively, keep Vercel's own Git integration for the website and use Actions only for Google Cloud and the server.

### Gaps
- Whether the SEFGH repository is user-owned or organization-owned, and on which GitHub plan, is unknown. That decides environment-secret availability and whether Vercel Hobby can connect to it (Hobby cannot connect to organization-owned repos).
- Whether the self-hosted runner charge was later reinstated is unknown; no source after December 2025 was found. A self-hosted runner on the future home server would avoid hosted minutes but adds a security risk for a private repo.
- `dorny/paths-filter`, `google-github-actions/deploy-cloudrun` and Kamal-from-Actions specifics were not fetched.

## 7. Configuration for easy switching: 12-factor environment variables, a provider registry per role, feature flags, and health checks and canaries before switching

### Takeaway
Make every host and provider choice an environment value read once at startup by a small Go `config` package: a per-role provider registry (summariser, embedder, reranker) with base URL, model, auth type and key reference, because Ollama, llama.cpp, vLLM, Agent Platform (Vertex) and most hosted APIs speak the OpenAI-compatible API. Keep the existing per-route rewrite switch for the API host. Put runtime toggles in a Postgres config table behind the OpenFeature Go SDK, which avoids Vercel Flags' Hobby limits. Switch only after a health check and a tagged or canary probe.

### Cited Findings
- OpenAI-compatible base URLs: Ollama `http://localhost:11434/v1/` (key ignored locally) — [Ollama](https://docs.ollama.com/api/openai-compatibility). llama.cpp `llama-server` has `/v1/embeddings`, `/v1/rerank`, `--api-key` and `/health` — [llama.cpp server](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md). vLLM's `vllm/vllm-openai` image serves an OpenAI-compatible API on port 8000 — [vLLM Docker](https://docs.vllm.ai/en/latest/deployment/docker.html)
- Agent Platform (Vertex) OpenAI-compatible base URL: `https://aiplatform.googleapis.com/v1/projects/{project_id}/locations/{location}/endpoints/openapi`. "Only Google Cloud Auth is supported", using an OAuth access token from Application Default Credentials that lives 1 hour by default. Only chat completions is shown — [OpenAI compatibility](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/start/openai)
- OpenFeature Go SDK: `github.com/open-feature/go-sdk` (package `openfeature`), latest v1.20.0, requires Go 1.26+. Use `openfeature.SetProviderAndWait(provider)` then `client.Boolean(ctx, "v2_enabled", true, evalCtx)`. It supports hooks (including a `slog` `LoggingHook`), events, an in-memory provider (`memprovider.NewInMemoryProvider`) and a test provider — [OpenFeature go-sdk](https://github.com/open-feature/go-sdk)
- Vercel Flags is in public beta. Hobby allows at most 10,000 flag requests per month (a request that evaluates many flags from one source counts once) and 100 flags and segments; Pro costs $0.03 per 1,000 flag requests — [Vercel Flags limits and pricing](https://vercel.com/docs/flags/vercel-flags/limits-and-pricing) (updated 2026-08-26)
- Health and canary hooks on each target: Kamal healthchecks `/up` before switching traffic — [Kamal proxy](https://kamal-deploy.org/docs/configuration/proxy/); Cloud Run tagged no-traffic revisions and percentage traffic — [Cloud Run rollouts](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration); llama-server `/health` returns 503 until the model is loaded — [llama.cpp server](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md); Vercel Daemons get a refreshed OIDC token file (`VERCEL_OIDC_TOKEN_FILE`) for calling other clouds without static keys — [Vercel Daemons](https://vercel.com/docs/daemons)
- Vercel Services private bindings inject a service's URL as an environment variable, and a rewrite destination can be a service — [Vercel Services](https://vercel.com/docs/services)

### Inferences
- **Configuration contract (proposal):** one prefix per role, for example `SEFGH_SUMMARISER_BASE_URL`, `SEFGH_SUMMARISER_MODEL`, `SEFGH_SUMMARISER_AUTH` (`bearer` | `gcp-adc` | `none`), `SEFGH_SUMMARISER_API_KEY` (or a `_FILE` path for secret mounts), with the same keys for `EMBEDDER` and `RERANKER`. Add `SEFGH_EMBEDDER_DIMENSIONS` and an `SEFGH_EMBEDDER_ID` that must match a value stored with the vectors. Parse into a typed Go struct at startup, fail fast on missing or invalid values, and log the resolved provider names (never keys). This keeps the standard-library-only rule: `os.Getenv` and `net/http` against `/v1/chat/completions`, `/v1/embeddings` and `/v1/rerank`.
- **Embedder is not freely switchable:** embedding model and dimensions are tied to the stored vectors (AGENTS.md). The embedder ID should be checked against the database at startup, and a mismatch should refuse to write rather than silently mix vector spaces. A model change is a migration plus re-embed.
- **Host switching:** keep the existing per-route rewrite switch. Add an origin variable (for example `GO_API_ORIGIN`) that the Next.js rewrite reads, so moving the Go API from Vercel to Cloud Run or the home server is one environment change plus a redeploy. Mind the 120 s proxied-request limit for external origins.
- **Worker trigger switching:** the worker exposes the same `run --stage=enrich --limit=N` CLI and an authenticated `POST /tick` handler. pg_cron (via an HTTP call), Cloud Scheduler, Vercel Cron, a Vercel Daemon loop or a systemd timer on the home server can then trigger it interchangeably. Progress and leases live in Postgres, so ticks are idempotent and a timeout or host change only resumes work.
- **Feature flags:** start with environment variables for deploy-time choices, plus a small `app_config` / `feature_flags` table in Postgres read through an OpenFeature provider for runtime toggles such as "Go handles route X" or "use summariser B for 10% of jobs". Tests use the in-memory provider. Vercel Flags' Hobby cap of 10,000 flag requests a month is too small to evaluate on every request and is tied to Vercel, which works against portability.
- **Switch checklist:** (1) deploy the new target with no traffic (Cloud Run `--tag`, a Vercel preview, or a Kamal deploy on a staging host); (2) wait for `/health` and the provider's `/v1/models` or `/health`; (3) run the contract fixtures and the production forwarding probe against the new origin; (4) shift traffic in steps (Cloud Run percentages) or flip the rewrite or origin variable; (5) keep the old target warm until the rollback window closes. No dual writes (AGENTS.md).

### Gaps
- No official 12-factor or OpenFeature provider-catalog page was fetched. A Postgres-backed OpenFeature provider for Go would need to be written (small) or chosen from the ecosystem directory, which was not checked.
- Hosted model-API pricing (Gemini, OpenAI-compatible third parties) and reranker availability per provider were outside this note's sources.
