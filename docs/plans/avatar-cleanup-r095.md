# R-095: serialized avatar replacement and cleanup

Owner approved recommendation A in decision pack2. This is the local implementation design required by the register. No SQL, policy change, cloud resource creation, activation or deployment is authorized here.

Before uploading, create the fixed own-folder object .avatar-upload-lock.png with upsert:false. All Go instances use this same key; Supabase documents that only the first concurrent non-overwriting upload succeeds. A duplicate returns409 with fixed retry text; other lock failures return503. Hold the lock through file creation, Auth/profile writes, compensation and cleanup. Release only an acknowledged acquired lock, with a separate one-second budget. An uncertain acquisition never deletes a potentially foreign lock. Source: https://supabase.com/docs/guides/storage/uploads/standard-uploads .

Create avatar filenames with one UTC millisecond stamp, a cryptographically random128-bit suffix and the detected extension; upload without overwrite. Failed writes remove only this unique new object (R-096). Listing completes before deletion so offsets do not skip entries when pages shrink. Read all100-entry pages, recurse through explicit folder entries, and delete old files in batches of100. Never select the current file or lock. Also preserve timestamps newer than the current upload as defense against an older non-participating writer. Invalid/cross-folder names are ignored. Cleanup remains bounded and best effort; a failed page causes no deletions from that partial snapshot.

Safety/liveness limits: all active upload writers must honor the protocol before rollout; the Next rollback handler does not. Hard termination or uncertain acquisition can leave a lock; it is never automatically expired or stolen. Recovery requires proving the owning request/process stopped, inspecting the exact user object and current profile, and an explicit operator action to remove only that lock. Do not delete by age or use privileged credentials in a request. This trades availability on crash for preventing a stale owner from removing a later owner's lock. Hosted same-key insert atomicity, lock permissions, cancellation/release and signed-in replacement remain rollout acceptance gates; local mocks are not that evidence.

## Accepted recovery decision

Owner decision 2026-10-31 (CLOSEOUT-001): accept manual crash-lock recovery and defer R-209 automatic recovery until after Phase 7. An operator must verify the owning request/process stopped and remove only the exact user lock after inspecting the current profile. Never remove by age or steal a potentially active lock. Hosted lock permissions, insert atomicity, signed-in replacement and participation by all active upload writers remain rollout gates. This decision authorizes no activation or deployment.
